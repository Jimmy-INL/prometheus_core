How this works

From ideas to teams in 30 minutes

Tracks and example ideas (10 min)

The next slides give three tracks and nine example agents. They are examples, not assignments; your own idea is welcome.

Informal pitches (10 min)

Anyone with an idea gets 60 seconds: the problem, who would use it, and which existing agent it would chain with.

Form teams (10 min)

4–5 people. Mix skills: someone comfortable with Docker, someone with domain knowledge, someone who likes prompts, someone who writes tests.

Register

Team name, members, idea, and one-line pitch go on the sign-up sheet. Pick up your Day 2 room.

A good hackathon agent…

  • solves one clear task someone at INL actually has
  • wraps an existing code, library, dataset, or document corpus
  • takes or produces an artifact (file in, file out)
  • can be demoed in a chat conversation within 5 minutes
  • chains with an agent that already exists
Scope for about one day of building. The platform does the plumbing; spend your time on the domain logic and a card the planner routes to.

Track A · Simulation & analysis

1 · Reactivity Coach  ·  2 · Decay-heat estimator

1 · Reactivity Coach

Pitch: "What happens if I insert $0.3 of reactivity in 0.5 s?" The agent solves 6-group point kinetics, plots power, period, and precursors, and explains the physics in plain language.

Skills: pk_simulate_transient (reactivity profile step/ramp/sine, β, Λ, delayed-group preset U-235/Pu-239 as an enum, duration) → CSV + PNG to DeepLynx + a JSON summary (peak power, prompt jump, stable period). pk_explain: an LLM explanation of a run artifact.

Uses: PrometheusWorker for the ODE solve, send_input_required when β is missing, artifacts.

Stretch: temperature feedback; inverse kinetics from an uploaded power trace (CSV, x_artifact_ref); a vision check of its own plot.

Chain: reuse reactor-dt-modules/openpointkinetics; workflow pk_simulate_transient → pk_explain.

2 · Decay-heat & shutdown-cooling estimator

Pitch: from a power history (constant or piecewise), estimate the decay-heat curve (an ANS-5.1-style fit, or Way–Wigner as a teaching approximation) and the cooling flow needed for a given ΔT, with plots and caveats.

Skills: decay_heat_curve (power_mwt, operating_time_days, shutdown_times, method enum) → CSV/PNG + JSON. cooling_requirement (decay-heat artifact, coolant water/sodium/helium, ΔT) → a mass-flow table.

Uses: deterministic compute via asyncio.to_thread, enum schemas, a 2-step workflow with x_input_source: runtime, a conversation message for "not for licensing use".

Stretch: an uncertainty band by Monte Carlo in the sandbox.

Chain: design (requirements_agent sizing) → decay_heat_curve → cooling_requirement.

Track A · Simulation & analysis

3 · Mesh QA & solver-readiness inspector

3 · Mesh QA inspector

Pitch: given any Exodus mesh artifact (for example the output of geometry_meshing), report element quality (scaled Jacobian, aspect-ratio histograms), the block and sideset inventory, and a "ready for MOOSE?" verdict with suggested fixes.

Skills: mesh_quality_report (mesh_artifact_id with x_artifact_ref, MIME application/x-exodus) → a JSON metrics artifact, histogram PNGs, and a markdown report. suggest_mesh_fixes: LLM.

Uses: get_artifact_file_path on a deeplynx:// URI, meshio/numpy (or pyvista in the sandbox), the vision flavor on renders.

Stretch: generate a MOOSE [Mesh] block with sideset names; compare two meshes.

The chaining workflow, ready to ship

id: <team>.step_to_checked_mesh
name: STEP to checked mesh
version: "1.0.0"
description: Mesh a STEP file, then check the mesh.
inputs: {required: [step_artifact_id]}
execution: {mode: sequential, max_concurrency: 1,
            on_error: fail_fast}
steps:
  - id: mesh
    skill_id: geometry_meshing
    params: {step_artifact_id:
             {from: input.step_artifact_id}}
    outputs: [{to_context: mesh_id, from: artifact_id}]
  - id: check
    skill_id: <team>_mesh_quality_report
    depends_on: [mesh]
    is_final: true
    params: {mesh_artifact_id: {from: context.mesh_id}}
outputs: {final: {from: step.check.result}}

Needs gmsh_agent running next to the platform. A mentor can help set it up.

Track B · Engineering data & tools

4 · MOOSE input doctor  ·  5 · Log triage

4 · MOOSE input-file doctor

Pitch: upload a MOOSE .i file. The agent parses the HIT blocks, explains the PDE system per variable (kernels → weak-form terms), flags suspicious BCs or units, and runs a syntax check.

Skills: moose_input_explain, moose_input_lint (rules + LLM), moose_input_diff (explain what changed between two inputs).

Uses: LLM tool calling with tools such as get_block, list_objects, lookup_object_doc; text artifacts; send_conversation_message for caveats.

Stretch: run a tiny case in a MOOSE container in the sandbox; emit a patch artifact.

Chain: open_pronghorn-agent (cfd_query) for documentation-backed answers; muninn (RAVEN wraps MOOSE inputs).

5 · Simulation log triage

Pitch: upload a failed MOOSE, RAVEN, or Cubit run log. The agent classifies the failure (non-convergence, mesh inversion, missing material property, license or environment), extracts the residual history into a plot, and proposes concrete input changes.

Skills: triage_log (log_artifact_id) → JSON diagnosis + residual PNG + suggested fixes; summarize_run.

Uses: regex extraction plus an LLM for classification, sandbox plotting, optional vision, conversation messages.

Stretch: hand off to the input doctor (#4) via a workflow; remember past failures in context state.

Chain: downstream of raven_workflow_execute (muninn), obstructed_pipe_cfd (open_pronghorn), run_transient (system-thermal-hydraulics).

Track B · Engineering data & tools

6 · DeepLynx dataset profiler

6 · Dataset profiler / notebook analyst

Pitch: "Profile the thermocouple data from yesterday's loop test." The agent finds the file in DeepLynx, pulls it into a sandboxed notebook, lets the LLM write pandas code in a run_python loop, and returns stats, anomaly flags, and plots, with the executed notebook as provenance.

Skills: profile_dataset (an artifact_id or a DeepLynx search query); ask_dataset (a free-form question answered through the code loop).

Uses: the agent-sandbox-mcp session loop (the agentic-hex-meshing pattern), a notebook artifact, StorageClient search or fsspec deeplynx://, budgets, vision on plots.

Stretch: IsolationForest anomaly detection from reactor-dt-modules/ml; save derived datasets back to DeepLynx with tags.

Chain: search_deeplynx (data-catalog-search-agent) → profile_dataset.

The sandbox loop, sketched

tools = [RUN_PYTHON, SUBMIT]          # ToolDefinition ×2
for step in range(MAX_STEPS):
    r = await llm.medium(history, tools=tools,
                         tool_choice="auto")
    if not r.tool_calls: break
    history.append(assistant_message(r))
    for call in r.tool_calls:
        if call.name == "submit": …
        cell = await session.run_cell(   # SandboxSession
            call.arguments["code"])
        await self.send_status_update(context,
            event_queue,
            message=call.arguments["summary"])
        history.append(tool_result_message(
            call, render(cell) + budget_note(step)))

Copy sandbox_client.py from gmsh_agent (branch agentic-hex-meshing): SandboxSession.run_cell(code) returns a CellResult, and it includes the Host: localhost header fix. The vision flavor needs an alias on a stock platform.

Track C · Safety, regulatory & documents

7 · Traceability matrix  ·  8 · Citation finder

7 · Requirements-to-test traceability matrix

Pitch: take the requirements JSON produced by requirements_agent, classify each requirement's verification method (inspection, analysis, test, or demonstration), build a requirements traceability matrix (XLSX/CSV), and flag untestable requirements.

Skills: classify_verification_methods (batched llm.medium with a forced tool whose schema is your pydantic output model); build_rtm → XLSX to DeepLynx.

Uses: structured output via tool calling, requires_approval for bulk regeneration, input-required for the component type.

Stretch: map rows to the 10 CFR 50 App. B criteria; per-row confidence; human edits through input-required.

Chain: requirements → classify_verification_methods → generate_testing_guides (component_testing_guide_agent).

8 · Regulatory citation finder ("NUREG Navigator")

Pitch: paste a design statement or requirement and get the relevant 10 CFR, NUREG-0800 SRP, Regulatory Guide, or ASME sections, with quoted rationale, as a citation table. It uses a small curated corpus of public NRC documents, indexed at startup.

Skills: find_regulatory_basis; compare_to_regulation (a gap check).

Uses: the embedding flavor (needs an embedding alias or a profile such as inl_litellm), context state, JSON artifacts with a json_type.

Stretch: a citation viewer served by add_static_endpoint; reranking with llm.small.

Chain: requirements_from_design → find_regulatory_basis; it feeds the component_* report agents and audit.

Track C · Safety, regulatory & documents

9 · Fault-tree builder

9 · Fault-tree builder from a system description

Pitch: from a text description or a topology JSON of a cooling system (for example requirements_agent's Alchemy topology graph), generate a fault tree for "loss of cooling". The output is machine-readable (JSON or OpenPSA MEF XML) plus a rendered SVG, and the minimal cut sets are computed in the sandbox.

Skills: build_fault_tree (topology_artifact_id or a description); compute_cut_sets; explain_dominant_failures.

Uses: an LLM tool loop with add_gate, add_basic_event, validate tools; sandbox compute; SVG and XML artifacts; requires_approval before publishing to DeepLynx.

Stretch: failure rates from a generic database table; importance measures (Fussell–Vesely, Birnbaum).

Chain: complements aegis (safety_analysis) and the non-A2A nuclear_safety_agent. Workflow: design → build_fault_tree → compute_cut_sets.

Tool loop as a builder

Instead of asking the LLM for a whole tree in one shot, give it small, validating tools. Each call mutates a tree kept in load_context_state/save_context_state, and validate reports orphans and cycles back to the model.

ADD_GATE = ToolDefinition.from_pydantic(
  "add_gate", GateArgs,
  description="Add an AND/OR gate under a parent")
ADD_EVENT = ToolDefinition.from_pydantic(
  "add_basic_event", EventArgs,
  description="Add a basic event (component failure)")
VALIDATE = ToolDefinition("validate",
  "Check the tree; returns problems or 'ok'")
The same builder pattern works for P&ID-to-topology, requirement sets, and workflow YAML generation.
Whatever you pick

A common baseline, and a way to split the work

Every team agent should

  • be scaffolded with setup_agent.py, with a team prefix on the card name and skill IDs
  • set "streaming": true and send meaningful status updates
  • call the LLM through self.llm_client(context, config=…) with LLMConfig.from_env().with_api_key(LITELLM_MASTER_KEY), flavor medium. small, vision, and embedding need aliases added to litellm_config.yaml (or another profile)
  • publish outputs with send_deeplynx_artifact or JSON artifacts with a correct mime_type
  • take file inputs through x_artifact_ref
  • ship one workflows/*.yaml that chains with an existing agent
  • have tests with a mocked EventQueue and LLM
  • live in its own repo (or a platform branch) with reviewed PRs
