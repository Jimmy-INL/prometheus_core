Day 2 preview

What "done" looks like on Day 2

Draft acceptance criteria. Organizers will confirm the final list; build toward these from the first hour.

Must have

  1. The agent is built from prometheus_agent_template and subclasses PrometheusAgent.
  2. It registers with the local platform and shows up under /agents in the chat.
  3. A natural-language request in the UI is routed to your skill by the orchestrator, not called by hand.
  4. It returns a structured result, and at least one artifact (JSON, file, or DeepLynx).
  5. Tests pass (uv run pytest) and lint is clean (uv run ruff check .).
  6. The code is in a repo with a PR that someone outside the team has reviewed.

Stretch

  1. It streams live status updates (capabilities.streaming: true).
  2. It uses the LLM through LLMClient, with the flavors that fit each task (small, medium, large, vision, embedding), possibly with tool calling.
  3. It asks the user for missing inputs (send_input_required) or needs plan approval (requires_approval).
  4. An agent-owned workflow YAML chains your skill with an existing agent.
  5. It consumes an uploaded file or another agent's artifact (x_artifact_ref).
  6. A 5-minute demo: the chat conversation, the artifact in a viewer, and a walkthrough of the code.

01

Platform architecture overview

From the big picture to one concrete chat turn: which services exist, what each does, and how a question becomes work done by specialist agents.

Why Prometheus

A chat front door to a team of specialist agents

Nuclear engineering work spans many specialized tools: meshing (Gmsh, Cubit), CFD (OpenPronghorn), UQ (RAVEN), BIM/IFC generation, requirements, safety analysis, literature search. Each needs expert setup.

Prometheus wraps each tool in an agent: a small web service that describes what it can do (its agent card) and accepts requests over a standard protocol (A2A).

An orchestrator (the client-agent) reads your chat message, plans which agents to call and in what order, asks you for missing inputs, and passes files (artifacts) between agents.

You, this hackathon

You write one agent. The platform handles the chat UI, planning, discovery, authentication, state, and file hand-off. Your code implements one method: _execute(params, context, event_queue).

The contract is the protocol

Any service that speaks A2A and publishes a card can join. It can live in the platform repo or in its own repo, and it registers itself at startup.

The big picture

Tiers of the platform

Client

The user and the web frontend. Today that is a React single-page app (the diagram's "e.g. Chainlit" is historical).

App server tier

The orchestrator agent, the state store (Valkey), and the LiteLLM gateway. LiteLLM is three things at once: agent registry, A2A gateway, and LLM proxy.

Agent runtime tier: pluggable slots

Any A2A-conformant agent registers and appears here. Each agent wraps a backend tool: a hosted service, licensed software, or an HPC code.

DeepLynx data layer

Stores uploads and agent outputs with provenance. deeplynx:// URIs let agents hand files to each other.

Model development pipeline

Long-term vision: training, validation, and a model registry that serves models to the gateway. Not needed for the hackathon.

One chat turn, end to end

From "Mesh this STEP file" to a mesh in the viewer

Browser → backend

POST /api/chat/messages {query, upload_ids…}. The browser authenticates with its session cookie and listens on one SSE stream, /api/events.

Backend → client-agent

A2A SendStreamingMessage with contextId = conversation ID and metadata.userToken = a per-turn RS256 identity JWT.

Plan

The planner LLM sees your query, the history, and every registered skill, and picks a skill or a workflow.

Missing inputs? Approval needed?

It replies needs_info (follow-up form) or plan_ready (Approve/Reject). Your next message continues the turn.

Dispatch

POST litellm:4000/a2a/{agent_name}, then LiteLLM forwards to the agent with Bearer AGENT_SECRET.

Agent works

_execute() runs. Status updates stream back through client-agent → backend → SSE to the UI as they happen.

Artifacts

Outputs are registered in the conversation catalog (Valkey). Files usually live in DeepLynx as deeplynx://….

Render

The backend attaches a render_hint (mesh, ifc, pdf, image, json…) and serves the bytes from /api/artifacts/{id}/content. The UI picks a viewer.

Inside the orchestrator

How the client-agent plans a turn

A multi-stage, schema-bound LLM pipeline (agents/client-agent/planner.py). It is a hand-written state machine; there is no LangGraph dependency despite what older docs say.

Turn resolutionstandalone task, clarification, or small talk?
Task decompositionlist required operations (without seeing capabilities)
Routing tool loopselect_capabilities, one workflow_<id> tool per workflow, set_operation_coverage … finalize_plan
Dependenciesorder multi-step plans
Parameter extractionfill inputSchema from the conversation
needs_info

Required params are missing, so a follow-up form is shown. The backend gives up after 5 rounds in a row.

plan_ready

A skill or workflow has requires_approval, so Approve/Reject is shown before anything runs.

completed

Single, sequential, or parallel execution finished; the result and new artifacts are returned.

fallback / unsupported

No agent covers an operation. Partial plans are never executed.

The planner only sees what your agent card says: skill description, usage_notes, tags, and parameter names, types, and descriptions. Writing a good card is half the work of getting routed.
Protocol

A2A v1 in one slide

{ "jsonrpc": "2.0", "id": "1",
  "method": "SendMessage",      // or SendStreamingMessage
  "params": {
    "message": {
      "messageId": "msg-1",
      "role": "ROLE_USER",
      "contextId": "conv-123",  // conversation
      "metadata": {
        "skillId": "geometry_meshing",
        "userToken": "<RS256 JWT>" },
      "parts": [ { "text": "{\"element_size\": 2.0}" } ]
    },
    "configuration": { "returnImmediately": false } } }

Headers:  A2A-Version: 1.0
          Authorization: Bearer <token>
  • JSON-RPC 2.0 over HTTP. One endpoint per agent (POST /); the method field selects the operation.
  • The skill goes in message.metadata.skillId, and the conversation in message.contextId.
  • Parameters travel as a JSON string in the first text part. The base class parses it into the params dict.
  • Tasks report exact states: TASK_STATE_WORKING, _COMPLETED, _FAILED, _INPUT_REQUIRED, _CANCELED…
  • The final answer is exactly one text part containing the JSON of the dict you returned.
  • Streaming is used only if the card says "capabilities": {"streaming": true}.
Older docs show v0.3 syntax (message/send, role: "user", params.context.skillId). Agents now reject it with -32601 Method not found.

What an artifact is

An ArtifactReference: artifact_id, name, description, and a uri or inline json_body/text_body, plus mime_type, json_type, tags and metadata. Scoped to one conversation.

How chaining works

The orchestrator passes the full catalog to every agent. Inputs marked x_artifact_ref in the card are filled automatically with the right artifact ID (a new upload, a name, or a UUID in the query).

How the UI shows it

The backend picks a viewer from json_type, then mime_type, tags, and file extension: VTK mesh (Exodus/STL), IFC, PDF, image, Mermaid, JSON, markdown report, or download.

Without DeepLynx configured, user uploads are not stored and agents cannot see them; you only get a status message. We set up a local DeepLynx in the deployment session.
